## 协议规范：MUST / SHOULD / MAY 要求重点部分汇总

MCP 协议遵循 BCP 14（RFC 2119 / RFC 8174）定义的关键词等级。

---

### 一、传输层（Streamable HTTP）

#### 端点与方法

| 要求                                                    | 等级 |
|-------------------------------------------------------|------|
| 服务器**必须**提供单个 HTTP 端点 /mcp，分别支持 POST 和 GET 方法         | **MUST** |
| 客户端**必须**在所有请求中包含 `MCP-Protocol-Version: <version>` 头 | **MUST** |
| 遇到无效/不支持的协议版本，服务器**必须**返回 `400 Bad Request`           | **MUST** |

#### HTTP POST（客户端 → 服务器）

| 要求 | 等级 |
|------|------|
| 每个 JSON-RPC 消息**必须**是一个新的 HTTP POST 请求 | **MUST** |
| 客户端**必须**在 `Accept` 头中同时包含 `application/json` 和 `text/event-stream` | **MUST** |
| POST 请求体**必须**是单个 JSON-RPC 请求、通知或响应 | **MUST** |

#### HTTP GET（服务器 → 客户端推送）

| 要求 | 等级 |
|------|------|
| 客户端**可以**发起 HTTP GET 打开 SSE 流接收服务器推送 | **MAY** |
| 客户端**必须**包含 `Accept: text/event-stream` 头 | **MUST** |
| 服务器**必须**返回 SSE 流，若不支持则返回 `405 Method Not Allowed` | **MUST** |

#### HTTP DELETE（会话终止）

| 要求 | 等级 |
|------|------|
| 客户端**应该**发送 DELETE + `Mcp-Session-Id` 头以显式终止会话 | **SHOULD** |
| 服务器**可以**返回 `405 Method Not Allowed` 若不支持客户端终止会话 | **MAY** |

#### 会话管理

| 要求 | 等级 |
|------|------|
| 服务器**可以**在初始化时通过 `Mcp-Session-Id` 头分配会话 ID | **MAY** |
| 会话 ID **必须**全局唯一且加密安全 | **MUST** |
| 若分配了会话 ID，客户端**必须**在后续所有请求中包含该头 | **MUST** |
| 若需要会话 ID 但未收到，服务器**应该**返回 `400 Bad Request` | **SHOULD** |
| 会话终止后，后续请求应返回 `404 Not Found` | — |

#### 断线重连

| 要求 | 等级 |
|------|------|
| 服务器**可以**为 SSE 事件附加 `id` 字段以支持断线重连 | **MAY** |
| 客户端可通过 `Last-Event-ID` 头恢复连接 | — |
| `id` **必须**在同一个会话内的所有流中全局唯一 | **MUST** |

#### 安全性

| 要求 | 等级 |
|------|------|
| **必须**验证所有连接的 `Origin` 头（防 DNS rebinding） | **MUST** |
| `Origin` 无效**必须**返回 `403 Forbidden` | **MUST** |
| 本地运行的服务**应该**仅绑定 `127.0.0.1` | **SHOULD** |
| **应该**对所有连接实施适当认证 | **SHOULD** |

### 二、生命周期（Initialization）

2025-11-25 稳定版是**有状态**协议：Initialization → Operation → Shutdown。

| 要求 | 等级 |
|------|------|
| 客户端**必须**先发送 `initialize` 才能发送其他消息（ping 除外） | **MUST** |
| `initialize` 必须包含 `protocolVersion`、`capabilities`、`clientInfo` | **MUST** |
| 服务器**必须**响应 `initialize`，返回协商后的版本、能力、服务端信息 | **MUST** |
| 客户端收到响应后**必须**发送 `notifications/initialized` | **MUST** |
| 服务器收到 `initialized` 前**不得**发送除 ping/logging 外的请求 | **MUST NOT** |
| 若客户端无法支持服务器返回的版本，**应该**断开连接 | **SHOULD** |
| 双方**必须**仅使用成功协商的能力 | **MUST** |

---

### 三、Tools（工具）

| 要求 | 等级 |
|------|------|
| 支持工具的服务器**必须**在 `capabilities` 中声明 `tools` | **MUST** |
| 服务器**应该**以确定性顺序返回工具列表 | **SHOULD** |
| 服务器**必须**验证所有工具输入参数 | **MUST** |
| 服务器**必须**实施适当访问控制 | **MUST** |
| 服务器**必须**对工具输出做安全过滤 | **MUST** |
| **应该**始终有人类确认机制，能拒绝工具调用 | **SHOULD** |
| 应用**应该**显示哪些工具暴露给了 AI 模型 | **SHOULD** |
| 应用**应该**在调用工具时给出清晰视觉指示 | **SHOULD** |
| 应用**应该**在操作前呈现确认提示 | **SHOULD** |
| 服务器**应该**限制工具调用频率 | **SHOULD** |
| 工具名称**应该** 1-128 字符，仅允许字母数字及 `_`、`-`、`.` | **SHOULD** |
| 工具名称**不得**包含空格、逗号等特殊字符 | **SHOULD NOT** |
| 同一服务器内工具名称**应该**唯一 | **SHOULD** |

---

### 四、授权（Authorization）

| 要求 | 等级 |
|------|------|
| 授权对 MCP 是**可选的** | **OPTIONAL** |
| HTTP 传输**应该**遵循 OAuth 2.1 | **SHOULD** |
| stdio 传输**不应**使用 OAuth，改为从环境获取凭据 | **SHOULD NOT** |
| 客户端**必须**实现 OAuth 授权服务器元数据（RFC 8414） | **MUST**（客户端） |

---

### 五、消息格式（JSON-RPC 2.0）

| 要求 | 等级 |
|------|------|
| 所有消息**必须**遵循 JSON-RPC 2.0 | **MUST** |
| 请求**必须**包含字符串或整数 ID，**不得**为 null | **MUST / MUST NOT** |
| 请求 ID **不得**在同一会话内重复使用 | **MUST NOT** |
| 结果响应**必须**包含与请求相同的 ID 和 `result` 字段 | **MUST** |

### 附：Draft 未来变更（2026-07-28 候选）

当前 Draft 正在向**无状态**协议过渡：

| 变更 | 说明 |
|------|------|
| ❌ 移除 `initialize`/`notifications/initialized` | 不再需要握手 |
| ❌ 移除 `Mcp-Session-Id` | 无会话 ID |
| ❌ 移除 `ping` | 协议层无心跳 |
| ✅ 新增 `server/discover` RPC | 替代 initialize |
| ✅ 每请求携带 `_meta` 元数据 | 协议版本、能力、客户端信息 |
